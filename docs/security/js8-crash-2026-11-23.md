# The JS8 app crashes of 2026-11-23: a use-after-free when the app closes

## Verdict

- **What it is:** a use-after-free of an LVGL object, not a heap overflow. A popup of the JS8 window (the "Save to
  log?" form) was closed with `lv_obj_del_async()`, and the window was closed before LVGL's timers next ran. The
  window took the popup with it (freed), then LVGL's queued delete ran `lv_obj_del()` on the freed memory.
- **Exploitable from the air: no.** Received JS8 can set the stage, and only partly. A `MSG` to our call opens the
  Inbox alert box (any station can send one). The log form opens only at the end of a QSO we transmitted in. Nothing
  received closes a popup or the window, and both have to happen in the same pass of the GUI loop. That takes the
  operator at the radio (two keys inside one 10 ms key read) or a browser paired with the OPERATE role (`js8 stop`,
  then `js8 close`, as the bench sent them). An unpaired network client is refused both commands.
- **Impact:** the GUI dies (SIGSEGV, or SIGABRT when glibc notices the damage). `x6100_daemon` restarts it in about
  2 s. This is memory corruption, but nothing an attacker sends lands in the freed memory before the bad delete
  runs (see below), so it is a crash, not code execution. A paired operator can already do anything with the radio.
- **Severity:** high for reliability (both bench radios crashed), low for security.
- **Fix:** `obj_later_del()` (`src/obj_later.c`) replaces `lv_obj_del_async()` for the windows' popups and maps: in
  JS8 (5 places), FT8 (2) and DMR (1), which had the same bug.
- **Verified:** on this Mac under AddressSanitizer, with the GUI's own LVGL 8.3 and `lv_conf.h`
  (`tools/js8_close_uaf`). The old sequence is caught as heap-use-after-free and the fixed one passes 19 checks.
  Both GUIs cross-build (no `ssp` in `readelf -d`). The received-text path was fuzzed under ASAN/UBSAN with no finding.
- **Not yet checked on the radios:** hot-install, then run `js8-text` both ways followed by `js8 close`, and
  `js8-close-to-g` (the main session, between test runs).

### What it does on the radio

LVGL there uses glibc's `malloc`/`free` (`LV_MEM_CUSTOM 1`) and checks no objects (`LV_USE_ASSERT_OBJ` 0).
`lv_obj_del()` on the freed popup reads its class, parent and `spec_attr`. It sends `LV_EVENT_DELETE` through the
event list `spec_attr` points to (function pointers), deletes the children it finds, and frees the object again.
Between the free and that delete, `close_window()` puts the previous button page back (`buttons_load_page()`).
That creates new LVGL objects of the same size, and glibc's tcache hands the freed chunks back last-in-first-out.
So the stale delete most likely deletes a live object of the next screen, and the GUI dies a moment later on the
dangling pointer. That fits both crashes: 1.3 s and about 3 s after the close, as the Sentry's page G came up. When
the chunk is left free instead, the result is a double free, which glibc reports with an abort.

## Exploitability

**Can a JS8 signal reach it?** It can only prepare it.

- The JS8 receive path never closes a popup or the window. Received messages go to the GUI thread through
  `ui_add_message()`, which returns once the window is closed (`src/js8_window.c:1489`). `destruct_cb()` stops the
  decoder (`rx_stop()`).
- Any station can open the Inbox alert box with a `MSG` to our call (the checksum is a CRC anyone can compute).
  Only a station we transmitted to can open the log form. Either way, the trigger is still someone at the radio, or a
  paired browser, closing a popup and the app in one GUI pass.

**Can it be triggered without the air?**

- **Remote server:** `js8 stop` and `js8 close` need a paired browser with the OPERATE role
  (`src/remote_server.c:2878`, `allowed()` `:2347`). The unpaired, and viewers, are refused.
- **At the radio:** `front_keys.c` hands LVGL every key waiting in one read (`continue_reading`). ESC on the popup
  then ESC on the list in the same 10 ms read would do it. That is unlikely by hand, and possible with a keyboard
  macro or a key-sending panel.

**Could the freed memory be filled with an attacker's bytes, for code execution?** Not from the air, and not by an
unpaired client.

- The window is short: the rest of that `scheduler_work()` pass, then the first timer of `lv_timer_handler()` (the
  async timer is put at the head of LVGL's timer list).
- Only the GUI's own allocations happen in it: the button page with its fixed labels, and the next queued items. No
  received text is allocated there, because the JS8 window is closed and its decoder stopped.
- A paired operator, who might queue commands into that pass, already controls the radio, so they gain nothing.

**The platform, checked read-only on both radios.** These raise what such a bug would be worth if the reuse could be
steered:

- `x6100_gui` is `ET_EXEC`, not PIE, at 0x10000.
- Its brk heap starts right after the binary (0x01872000 on the X6200, 0x01866000 on the X6100). With
  `randomize_va_space = 1`, the stack, mmap and libraries are randomized, but not the brk heap.
- Partial RELRO (no `BIND_NOW`), NX (`GNU_STACK` RW, heap `rw-p`), no stack protector, `_FORTIFY_SOURCE=1`.
- So a fake `lv_obj_t` with a chosen event callback would give code execution with no address leak needed. This is
  why the fix covers every window with the pattern, not only JS8.

**Compared with the FT8 `stoi` DoS** (f2f6b8b3, PR #253, and the review fixes in b55b31a): that one was over the air
and needed no conditions. Any station's FT8 free text `A B +` ended the GUI with an uncaught exception, a clean
abort with no memory damage. This one cannot be reached over the air. It corrupts memory, but needs the operator or a
paired browser to trigger it.

**Is there a heap overflow on the receive path?** None was found. An ASAN/UBSAN fuzz harness put 300,000 random
12-character decoder frames, with random frame bits, through the receive path. That path is js8core's unpacking
(varicode, JSC) in `FrameRenderer::render`, then `MessageAssembler`, then `classify`, then the copy into
`js8_rx_msg_t` as `to_msg()` makes it. From there the frames, and 300,000 structured texts at and over the
639-character limit, went through the window's C logic: stations, QSO book, `js8_process()` auto-answer, inbox,
held store, alert words and the `@X6100` test: 968,022 messages in all. There was no report. The JSC decompressor already bounds its
dictionary index (`third-party/js8core/src/protocol/jsc.cpp`, the `base[]` and `JSC_SIZE` checks). The harness is
`js8_rx_fuzz.cpp` in the session's notes folder; it is not a host check.

## The fix

`src/obj_later.c`, `obj_later_del(obj)`, in place of `lv_obj_del_async()` for a window's children:

- The object waits in a short list and is deleted at the next `lv_timer_handler()`, as before. The deferred delete is
  our own async call, which reads only that list.
- Each waiting object gets an `LV_EVENT_DELETE` handler that takes it off the list. When it goes some other way first
  (with its window, as here), it is forgotten at that moment, so the deferred delete never sees freed memory,
  whatever the order of events.
- Asking twice deletes once, and a waiting parent and child are each deleted once.
- Over 32 waiting at once (a window has about a dozen popups), it falls back to LVGL's way and logs it once.

Two simpler fixes would not work:

- **Deleting at once:** popups close from their own buttons (Cancel, Save), and LVGL still uses the button after the
  callback returns.
- **Checking `lv_obj_is_valid()` before the delete:** the freed address is typically reused by the next screen's
  objects, exactly as here, and the check would then pass and delete the wrong object.

Changed:

- `src/js8_window.c`: `list_forget()`, `p3_popup_shut()`, `p3_popup_drop()`, `alert_close()`, `map_close()`
- `src/ft8_window.c`: `map_close()`, `freq_close()`
- `src/dialog_dmr.c`: `map_close()`
- `src/CMakeLists.txt`

`app_window.c` is unchanged: the DELETE hook makes the order of the close irrelevant.

## How it was verified

- **`make -C tools/js8_close_uaf`** (also run by `tools/host_checks.sh` and CI, like every `tools/*/Makefile`). It
  builds the GUI's LVGL with ASAN and UBSAN, in parallel, in seconds. Then:
  1. No `lv_obj_del_async(` is left in `js8_window.c`, `ft8_window.c` or `dialog_dmr.c`. On the unfixed tree this
     fails and lists the 8 places.
  2. The old sequence must be stopped by AddressSanitizer as heap-use-after-free. This proves the harness still
     reproduces the crash.
  3. The same sequence with `obj_later_del()`, plus the helper's cases: shut from its own button with the window
     closing in the same pass, a plain deferred delete, asked twice, parent and child, the next screen's objects at
     reused addresses left alone, and 40 at once. Result: 19 of 19 checks.
- **Cross builds** of the X6200 and X6100 GUIs from this tree, in folders of their own (`build/x6200/gui-uafchk`,
  `build/x6100/gui-uafchk`). Both compile, and `readelf -d` shows no `ssp`.
- **Not on the radios yet.** A hot install on both, then `js8-text x6100>x6200` and `js8-text x6200>x6100` (each
  ending with `js8 stop` and `js8 close` while the log form is up), then `js8-close-to-g`. Both GUIs must stay up.

## Residual risk

- **Audio thread against close.** `dialog_audio_samples()` (`src/app_window.c:269-272`) reads `shown` twice with no
  lock, and `dialog_destruct()` sets it to NULL. The JS8 `audio_cb()` (`src/js8_window.c:1774`) reads `rx` while
  `rx_stop()` (`:1746`) destroys it. `d->run` goes false long before `rx_stop()`, so the window is a few instructions
  on a preempted audio thread. That is theoretical, and not these crashes, but worth a lock or an atomic hand-over.
- **The X6100's `free(): invalid next size (fast)` at 14:21Z** is unexplained: heap damage that glibc found later.
  This bug class in FT8 or DMR (now fixed) is one candidate. A GUI built with ASAN for the host (Linux or Docker) and
  driven through the same apps would settle it.
- **Other async callbacks that carry an object pointer:** `src/spectrum_view.c:775` (an invalidate, on the main
  screen's long-lived spectrum). It is not a window child, so it is not affected now.
- **`src/screen_saver.c:351`** still uses `lv_obj_del_async()`, on the screen saver over the top layer. It is not
  inside a window, so it is not affected.
- **JS8 decoding trouble** (partial or odd texts) was not looked into beyond the fuzz, which found no memory fault on
  that path.
